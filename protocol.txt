= Beanstalk Protocol (beanstalkd-pi) =

This file documents beanstalkd-pi's wire protocol as a diff against
upstream beanstalkd's own spec, vendored read-only in this repo at
beanstalkd/doc/protocol.txt (git submodule, C reference implementation).
Read that file first for the full protocol (error replies, every
command's arguments and replies, stats keys, and so on); it applies to
beanstalkd-pi unchanged except where noted below. This file only records
where beanstalkd-pi's wire behavior diverges from it, plus the eight
extension commands that have no stock equivalent at all.

Everything about this implementation that is not part of the wire
protocol itself (what the program is, CLI flags, persistence, process
lifecycle, concurrency model, the observability HTTP server, and so on)
lives in documentation.txt instead, not here.

Job Lifecycle
-------------

Identical to stock beanstalkd: job.go implements exactly these four
states ("ready", "reserved", "delayed", "buried") and these transitions,
driven by the same commands.

   put            reserve               delete
  -----> [READY] ---------> [RESERVED] --------> *poof*



   put with delay               release with delay
  ----------------> [DELAYED] <------------.
                        |                   |
                        | (time passes)     |
                        |                   |
   put                  v     reserve       |       delete
  -----------------> [READY] ---------> [RESERVED] --------> *poof*
                       ^  ^                |  |
                       |   \  release      |  |
                       |    `-------------'   |
                       |                      |
                       | kick                 |
                       |                      |
                       |       bury           |
                    [BURIED] <---------------'
                       |
                       |  delete
                        `--------> *poof*

Tube lifetime differs slightly: a tube is also kept alive by a reserved
job (a job's reservation does not release its tube), and beanstalkd-pi
adds a "delete-tube" extension that can purge a tube's jobs on demand
rather than only through this reference-counted GC. See "Extension
Commands" below and documentation.txt for the full account.

Differences from stock
-----------------------

Error replies:

 - OUT_OF_MEMORY is never sent. beanstalkd-pi's data structures grow with
   the Go runtime's ordinary heap allocator instead of a fixed-size
   in-process store, so a client never observes this reply; a real
   allocation failure crashes the process (as any Go program does on
   OOM) rather than being reported over the wire.

 - INTERNAL_ERROR is never sent; not part of this server's error
   vocabulary.

 - UNKNOWN_COMMAND: eight commands beyond stock's set are recognized
   instead of producing this reply — see "Extension Commands" below.

put:

 - max-job-size is exactly 65536 bytes here (a body of 65536 bytes is
   accepted; 65537 or more is rejected), one byte larger than stock's
   actual default of 2**16-1 (65535) despite the spec's "default: 2**16"
   wording. There is no flag to change it at runtime.

 - BURIED is never sent from put, for the same reason as OUT_OF_MEMORY
   above — there is no fixed-size priority queue to run out of memory
   growing. put only ever answers INSERTED, JOB_TOO_BIG, DRAINING, or
   EXPECTED_CRLF.

 - See also "put-at" under "Extension Commands" below, which takes an
   absolute Unix timestamp instead of a relative delay.

reserve / reserve-with-timeout:

 - Blocking and DEADLINE_SOON/TIMED_OUT firing are driven by a 100ms
   polling tick loop rather than stock's timer-heap-driven event
   reactor; the wire-visible timing is the same to within that
   resolution.

release:

 - BURIED is never sent, for the same reason as OUT_OF_MEMORY above.
   release only ever answers RELEASED or NOT_FOUND.

 - If the job's tube has dead-letter routing configured (see "set-dlq"
   under "Extension Commands" below) and this release pushes its
   release-plus-timeout count to the configured threshold, the job is
   buried in the configured dead-letter tube instead of being re-queued
   in its own tube. The reply is still RELEASED either way — from the
   releasing client's point of view it released the job; where the job
   ends up next is server-side routing, same as it always was.

kick:

 - See also "kick-tube" under "Extension Commands" below, which applies
   this same kick semantics to a named tube instead of only the
   currently used one.

peek-ready / peek-delayed / peek-buried:

 - See also "peek-tube" under "Extension Commands" below, which applies
   this same peek semantics to a named tube instead of only the
   currently used one.

stats-job:

 - "file" is always 0. There is no binlog, so this field is present only
   for client parsers that expect the key to exist.

 - "kicks" is immediately followed by "dlq-from-tube", an extra key with
   no stock equivalent — see "set-dlq" under "Extension Commands" below.
   It is the name of the tube this job was automatically dead-lettered
   out of, or "" (empty) if that never happened. Stock clients ignore
   unknown stats keys, so this is transparent to them.

stats-tube:

 - "pause-time-left" is immediately followed by "dlq-max-attempts" and
   "dlq-tube", two extra keys with no stock equivalent — see "set-dlq"
   under "Extension Commands" below. "dlq-max-attempts" is 0 when
   dead-letter routing is disabled for this tube; "dlq-tube" is the
   configured destination tube name, or "" (empty) when disabled. Stock
   clients ignore unknown stats keys, so this is transparent to them.

stats:

 - "cmd-put" is immediately followed by "cmd-put-at", an extra key with
   no stock equivalent — see "Extension Commands" below. Stock clients
   ignore unknown stats keys, so this is transparent to them.

 - "cmd-kick" is immediately followed by "cmd-kick-tube", an extra key
   with no stock equivalent — see "Extension Commands" below. Stock
   clients ignore unknown stats keys, so this is transparent to them.

 - "cmd-pause-tube" is immediately followed by "cmd-delete-tube", an
   extra key with no stock equivalent — see "Extension Commands" below.

 - "cmd-peek-buried" is immediately followed by "cmd-peek-tube", an extra
   key with no stock equivalent — see "Extension Commands" below.

 - "cmd-stats-tube" is immediately followed by "cmd-stats-conn", an extra
   key with no stock equivalent — see "Extension Commands" below.

 - "cmd-list-tubes-watched" is immediately followed by
   "cmd-list-connections", an extra key with no stock equivalent — see
   "Extension Commands" below.

 - "cmd-ping" is immediately followed by "cmd-set-dlq", an extra key with
   no stock equivalent — see "Extension Commands" below.

 - "job-timeouts" is immediately followed by "job-dead-lettered", an
   extra key with no stock equivalent: the total number of jobs
   automatically routed to a dead-letter tube by "set-dlq" (see
   "Extension Commands" below).

 - All five binlog-* fields ("binlog-oldest-index",
   "binlog-current-index", "binlog-max-size", "binlog-records-written",
   "binlog-records-migrated") are hard-coded to 0. There is no binlog
   (see documentation.txt); these keys exist only for client parsers
   that expect them to be present.

--------------------------------------------------------------------------
Extension Commands
--------------------------------------------------------------------------

The eight commands below have no equivalent in stock beanstalkd's protocol.
A stock client that sends any of these command names against stock
beanstalkd receives UNKNOWN_COMMAND, so none of them can collide with, or
shadow, a stock command; beanstalkd-pi recognizes them in addition to the
full stock set. Nothing else in stock's protocol is affected by their
presence.

The "ping" command is a bare liveness check. Its form is:

    ping\r\n

The response is always:

    PONG\r\n

There is no error case beyond the ones common to all commands (BAD_FORMAT,
UNKNOWN_COMMAND). Increments the "cmd-ping" stats counter.

The put-at command is "put" with an absolute schedule time instead of a
relative delay — useful for "run at midnight" or any other job whose
target time is more naturally a timestamp than an offset from now, without
the client having to compute (and keep re-computing, if queueing is slow
or retried) "target time minus current time" itself, which drifts under
clock skew or a slow producer. Its form is:

    put-at <pri> <unix-ts> <ttr> <bytes>\r\n
           <data>\r\n

 - <pri>, <ttr>, <bytes>, and <data> have the same meaning as in "put".

 - <unix-ts> is an integer number of seconds since the Unix epoch (UTC),
   the absolute time at which the job should become ready. A timestamp at
   or before the current time behaves like "put"'s delay 0: the job is
   ready immediately. There is no upper or lower bound beyond fitting in a
   64-bit signed integer.

The job's actual wake time is resolved from <unix-ts> against the clock at
the moment the job is enqueued (after its body has been fully read), not
when the command line is parsed, so time spent reading a large body never
pushes the job's ready time later. Once enqueued, a delayed put-at job is
indistinguishable from a delayed put job: it sits in the same per-tube
delay heap, is promoted to ready by the same tick loop, and — like put —
only ever answers INSERTED, JOB_TOO_BIG, DRAINING, or EXPECTED_CRLF (see
"put" above for why BURIED and OUT_OF_MEMORY are never sent). A malformed
command line replies BAD_FORMAT. Increments the "cmd-put-at" stats counter
(see the "stats" command above); "cmd-put" is unaffected by put-at calls.

The kick-tube command is "kick" restricted to an explicit tube instead of
the connection's currently used tube — useful for an operator kicking a
tube they are not otherwise using. Its form is:

    kick-tube <tube> <bound>\r\n

 - <tube> is a name at most 200 bytes, the tube to kick.

 - <bound> is an integer upper bound on the number of jobs to kick, same
   meaning as in "kick".

Semantics on the named tube are identical to "kick" on the currently used
tube, including the preference for buried jobs over delayed jobs. The
response is one of:

 - "KICKED <count>\r\n" — <count> is an integer indicating the number of
   jobs actually kicked, same as "kick"'s reply.

 - "NOT_FOUND\r\n" if the named tube does not exist.

A malformed command line replies BAD_FORMAT, exactly as "kick" does.
Increments the "cmd-kick-tube" stats counter (see the "stats" command
above).

The delete-tube command deletes every ready, delayed, and buried job in the
named tube outright, without requiring each to be reserved and deleted
individually. Its form is:

    delete-tube <tube>\r\n

 - <tube> is a name at most 200 bytes, the tube to purge.

The response is one of:

 - "DELETED <count>\r\n" — <count> is an integer indicating the number of
   jobs purged synchronously. A job still reserved by another connection at
   the time of this command is not included in <count>: it is deleted
   later, asynchronously, once that connection releases, buries, times out
   on, or disconnects while holding it, rather than being allowed to return
   the job to the tube (see documentation.txt's Tube GC section for the
   full mechanism).

 - "NOT_FOUND\r\n" if the named tube does not exist.

A fresh "put" into the tube afterward works normally. The "default" tube's
jobs can be purged the same way, but — like stock's process-lifetime
default tube — "default" is never removed from the tube map by this or any
other command. Increments the "cmd-delete-tube" stats counter (see the
"stats" command above).

The peek-tube command is "peek-ready"/"peek-delayed"/"peek-buried"
restricted to an explicit tube instead of the connection's currently used
tube — useful for an operator inspecting a tube they are not otherwise
using, without the use/peek/use-back round trips that would otherwise be
needed (and which would mutate connection state along the way). Its form
is:

    peek-tube <tube> <state>\r\n

 - <tube> is a name at most 200 bytes, the tube to inspect.

 - <state> is one of "ready", "delayed", or "buried", selecting which of
   the tube's queues to peek into — same meaning as the "ready"/"delayed"/
   "buried" halves of "peek-ready"/"peek-delayed"/"peek-buried".

Semantics on the named tube are identical to peek-ready/peek-delayed/
peek-buried on the currently used tube: peek-tube <tube> ready returns the
next ready job, peek-tube <tube> delayed the delayed job with the shortest
delay left, and peek-tube <tube> buried the next job in the buried list
(oldest first). The response is one of:

 - "FOUND <id> <bytes>\r\n<data>\r\n" — same reply as "peek-ready" etc.

 - "NOT_FOUND\r\n" if the named tube does not exist, or exists but has no
   job in the requested state.

A malformed command line (wrong number of arguments, an invalid tube name,
or a <state> other than "ready"/"delayed"/"buried") replies BAD_FORMAT.
Increments the "cmd-peek-tube" stats counter (see the "stats" command
above); "cmd-peek-ready"/"cmd-peek-delayed"/"cmd-peek-buried" are
unaffected by peek-tube calls.

The stats-conn command returns introspection stats about a connection —
the single most useful thing missing from stock's introspection
commands, since stock has no notion of a connection as something a
client can inspect at all. Its form is:

    stats-conn [id]\r\n

Unlike stats-job/stats-tube, its argument is optional. With no <id>, it
reports on the calling connection itself, so a client that has no other
way to learn its own connection id (e.g. for correlating with
list-connections, or with a log line elsewhere) can retrieve it here.
With <id> given, it reports on the connection with that id instead
(matching the "id" field from list-connections or a stats-conn reply),
letting one connection inspect another's stats directly instead of
scanning list-connections for it.

If <id> is given, the response is:

    OK <bytes>\r\n
    <data>\r\n

or, if no connection with that id currently exists:

    NOT_FOUND\r\n

With no <id>, the response is always:

    OK <bytes>\r\n
    <data>\r\n

<data> is a YAML mapping with the following keys, in this order:

 - "id" — the connection's id (matches the "id" field in list-connections,
   and correlates with the "conn" field in beanstalkd-pi's own logs).

 - "addr" — the connection's remote address, as text (host:port).

 - "tube" — the name of the connection's currently used tube (the one
   "put" inserts into).

 - "watching" — a YAML flow-style list of the names of every tube the
   connection is watching (the tubes "reserve" draws from), e.g.
   "[default, foo]".

 - "reserved-jobs" — a YAML flow-style list of the ids of every job the
   connection currently holds reserved, e.g. "[101, 102]", or "[]" if it
   holds none.

 - "producer" — "true" if the connection has ever sent "put"/"put-at",
   else "false".

 - "worker" — "true" if the connection has ever sent
   "reserve"/"reserve-with-timeout"/"reserve-job", else "false".

 - "waiting" — "true" if the connection is currently blocked in a reserve
   call, else "false".

Besides the ones common to all commands (BAD_FORMAT, UNKNOWN_COMMAND),
the only error case is NOT_FOUND, when an <id> is given and no
connection with that id currently exists. Increments the
"cmd-stats-conn" stats counter (see the "stats" command above).

The list-connections command returns the same fields as stats-conn for
every currently connected client, answering questions stats-conn can't —
e.g. "which connection is holding job 4711, and what tubes is it
watching". Its form is:

    list-connections\r\n

The response is always:

    OK <bytes>\r\n
    <data>\r\n

<data> is a YAML sequence of mappings, one per connection, each with the
same "id"/"addr"/"tube"/"watching"/"reserved-jobs"/"producer"/"worker"/
"waiting" keys as stats-conn, ordered by ascending connection id. The
sequence is empty ("---\n") only in the impossible case of no connections
at all — the caller itself is always a connection, so it always includes
at least one entry. There is no error case beyond the ones common to all
commands (BAD_FORMAT, UNKNOWN_COMMAND). Increments the
"cmd-list-connections" stats counter (see the "stats" command above).

The set-dlq command configures automatic dead-letter routing for a tube:
once a job in that tube has failed delivery (been released, or timed out
on its TTR) enough times, it is buried in a separate tube instead of
being handed back to workers again — the same idea as SQS's or RabbitMQ's
dead-letter queue, adapted to reuse beanstalkd's existing "buried" state
and existing tube-inspection commands (peek-tube, kick-tube, stats-tube,
delete-tube) rather than adding a fifth job state or dedicated DLQ
commands. Its form is:

    set-dlq <tube> <max-attempts> <dead-tube>\r\n

 - <tube> is a name at most 200 bytes, the tube to configure. Unlike
   pause-tube/kick-tube/delete-tube/peek-tube, <tube> need not already
   exist: like "use", it is created if missing, so DLQ policy can be set
   up before any producer has touched the tube.

 - <max-attempts> is an integer. 0 disables dead-letter routing for
   <tube> (the default for every tube, and the prior behavior of this
   server: a job can be released or time out any number of times and
   always goes back to its own tube). A nonzero value is the number of
   failed deliveries — releases plus TTR timeouts, added together — a job
   must accumulate before it is dead-lettered.

 - <dead-tube> is a name at most 200 bytes, the tube a job is buried into
   once it crosses the threshold. It is validated but not required to
   exist yet, and — deliberately, unlike <tube> — not created by this
   command either: it only comes into existence once a job is actually
   routed into it, so configuring DLQ policy that never fires never
   clutters list-tubes with an empty tube. <dead-tube> may be the same as
   <tube>, which degenerates into "bury this tube's job in place after
   <max-attempts> failed deliveries" — a valid way to use this command
   without a second tube at all. Ignored (but still validated) when
   <max-attempts> is 0.

A dead-lettered job is buried, not made ready, in <dead-tube> — exactly
as if a worker on <dead-tube> had reserved and buried it — so it is
recoverable with the same tools as any buried job (peek-tube <dead-tube>
buried, stats-job, kick-tube <dead-tube> to make it reservable again,
delete-tube <dead-tube> to discard it). Landing it buried rather than
ready is also what keeps this mechanism from ever looping on its own:
even a <dead-tube> that points back at <tube>, or a cycle across several
tubes' DLQ configs, cannot re-trigger automatically, because a buried job
only becomes reservable again via an explicit kick. Manual "bury" is
unrelated and never triggers dead-letter routing — set-dlq only ever
intercepts a job on its way back to Ready after release or a TTR timeout.

Once dead-lettered, a job's "tube" (in stats-job) becomes <dead-tube>,
and its release/timeout counts keep counting from where they left off; if
<dead-tube> has its own set-dlq policy, a job kicked back to ready there
and then released/timed out enough times is dead-lettered again under
that policy, same as any other tube. stats-job gains a "dlq-from-tube"
key naming the tube a job was routed out of (see "stats-job" above), and
stats-tube gains "dlq-max-attempts"/"dlq-tube" keys reporting a tube's
current configuration (see "stats-tube" above).

Dead-letter configuration is in-memory only, exactly like pause-tube's
pause state: it is not persisted, so it resets to disabled across a
restart. A dead-lettered job's "dlq-from-tube" value on a job, unlike the
tube configuration that produced it, is ordinary job state and is
persisted/recovered like any other job field.

The response is always "DLQ_SET\r\n". Besides the ones common to all
commands (BAD_FORMAT, UNKNOWN_COMMAND), there is no error case — there is
no NOT_FOUND, since <tube> is created rather than required to exist.
Increments the "cmd-set-dlq" stats counter (see the "stats" command
above).
